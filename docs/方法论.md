# 方法论：这支片子为什么成立

> 结论先说：它赢的不是「剪得更好」，是**交付工程**。
> 同样 123 秒，我们上一版是「一段能播的视频」，这一版是「一套能改、能验、能复刻的片子」。

---

## 1. 单一时间轴真相

`film/timing.json` 里 17 个镜头、每镜的 `from / duration / voiceFrom / voiceDuration`，画面切点、字幕起落、音效钉点、旁白入点**全部从这一个文件派生**。

- 为什么有效：改一处，全片跟着对；不会出现「画面改了字幕没改」。
- 我们的反例：字幕、卡片、片段各写一套时间码，改一次要改三处，最后谁也不知道哪个是对的。

**规矩**：时间只写在一个地方，其它地方只能引用。

---

## 2. 影片即代码

片子是 Remotion 组件（`film/*.tsx`），不是时间线工程文件。

- 能 diff、能 review、能重渲染、能批量改文案。
- 换字号、换字卡、换节奏 = 改常量 + 重渲染，不用重剪。
- 我们的反例：ffmpeg 一把梭，改一句字幕就得整条重跑，且中间产物不可查。

**规矩**：能用代码描述的镜头，不要用手拖。

---

## 3. 素材先本地化，并且记来源

`public/` 里是全部素材，`docs/sound-sources.md`、`typography-sources.md`、`music-provenance.json`、`licenses/` 记着每个字体和音效从哪来、什么授权。

- 为什么有效：交付给别人时，包能独立跑；平台审核、版权争议时有据可查。
- 我们的反例：素材散在几个目录、来源靠记忆，换台机器就断链。

**规矩**：素材进包，来源进台账。

---

## 4. 交付物必须可编辑

除了成片，还交付一台编辑台（`src/`）：改标题、改字幕、拖时间、换素材、导出 JSON、导出视频。

- 为什么有效：接收方不需要会 Remotion 也能改；修改可以回传成 JSON。
- 我们的反例：只给 mp4，对方想改一个字只能重做。

**规矩**：交付 = 成片 + 可改的工程 + 能改工程的界面。

---

## 5. 验收要留记录，不是「我看过了」

- `文件校验.json`：每个文件的哈希。
- `docs/delivery-qa.json`：成片 sha256 + 视频比特流哈希 + 完整解码通过 + 多版本一致性。
- `验收记录.md`：独立解压到带中文空格的新目录 → `npm ci` 262 个依赖 → typecheck → build → 编辑器载入 17 镜 / 66 字幕 / 127 片段 / 5 轨 → 改一个字 → 导出 JSON → 导出视频 → 抽帧确认。
- 还扫了凭据、绝对路径、CRC。

**规矩**：验收不是一个动作，是一份能给别人看的记录。

---

## 6. 独立复核，逐条对规则

`docs/independent-review.md` 是**另一个 reviewer** 写的：产品一致性 / 数据真实性 / 音频节奏 / aesthetic-rules 逐条 / 必须修复项 / 建议优化项 / 无法验证项。

- 关键是最后两类：**「无法验证项」** 明确列出——这比假装全验过可信得多。

**规矩**：自己剪完不算完，得有人按清单对着打勾，并且敢写「这条我验不了」。

---

## 7. 用户的修正写进文档

`production-spec.md` 有一节叫「用户最新视觉修正」。

- 为什么有效：改动的**理由**留下来了，下次不会又改回去。

**规矩**：每次被退回，不是因为「不好看」，而是因为「不符合某条已写下的规则」——所以规则要先写下来。

---

## 一句话复述

> 把片子当成一个**可验证的软件交付物**：单一真相、代码化、素材可溯、可编辑、有记录、有复核。
